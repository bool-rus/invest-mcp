## Purpose

Текущие рыночные данные и история через MCP: последняя цена, снэпшот стакана, исторические свечи и серверная подписка на обновления стакана через ресурсы с push-нотификациями.

## ADDED Requirements

### Requirement: get_last_price
Сервер SHALL предоставлять инструмент get_last_price с параметром instrument (одиночная ссылка или список). Результат — для каждого инструмента: figi, price (десятичная строка), time. Если по инструменту нет сделок — price SHALL быть null c признаком отсутствия данных.

#### Scenario: Текущая цена инструмента
- **WHEN** вызывается get_last_price для figi инструмента
- **THEN** возвращается последняя цена сделки с временем

### Requirement: get_order_book
Сервер SHALL предоставлять инструмент get_order_book с параметрами instrument и depth (целое от 1 до 50, по умолчанию 20). Результат — снэпшот: упорядоченные bids (покупки) и asks (продажи) с ценами и объёмами, последняя цена, минимальный шаг цены, лимиты. Глубина вне диапазона SHALL отклоняться ошибкой валидации.

#### Scenario: Снэпшот стакана
- **WHEN** вызывается get_order_book для figi с depth=10
- **THEN** возвращается до 10 уровней покупки и продажи с ценами и объёмами

#### Scenario: Некорректная глубина
- **WHEN** вызывается get_order_book с depth=0 или depth=51
- **THEN** инструмент возвращает ошибку валидации

### Requirement: get_candles
Сервер SHALL предоставлять инструмент get_candles с параметрами instrument (ссылка), interval (1min, 2min, 3min, 5min, 10min, 15min, 30min, 1hour, 2hour, 4hour, 1day, 1week, 1month), from и to (RFC3339), необязательным limit. Результат — массив свечей, отсортированный по времени открытия: time, open, high, low, close (десятичные строки в формате capability instruments), volume, is_complete. Период свыше лимитов брокера SHALL обрабатываться без потери данных (разбиение на подзапросы с последующей склейкой).

#### Scenario: Свечи за период
- **WHEN** вызывается get_candles для figi с interval=1hour за период в один день
- **THEN** возвращаются часовые свечи от from до to с ценами OHLC и объёмом

#### Scenario: Разбиение длинного периода
- **WHEN** запрошенный период превышает лимит брокера на один запрос
- **THEN** сервер разбивает запрос на подзапросы и склеивает свечи без пропусков и дублей

#### Scenario: Некорректный интервал
- **WHEN** interval не распознан
- **THEN** инструмент возвращает ошибку валидации

### Requirement: Подписка на стакан через ресурс
Сервер SHALL предоставлять resource template orderbook://{figi}/{depth}. read_resource SHALL возвращать текущий снэпшот стакана. При подписке subscribe сервер SHALL поддерживать живой стрим стакана (через Invest API) и при каждом изменении отправлять нотификацию resources/updated по URI подписки. После unsubscribe поток данных для этого подписчика SHALL прекращаться. Подписчики на один figi SHALL переиспользовать общий стрим.

#### Scenario: Чтение ресурса
- **WHEN** клиент вызывает read_resource для orderbook://TCS80A107UL4/20
- **THEN** возвращается текущий снэпшот стакана с глубиной 20

#### Scenario: Обновления после подписки
- **WHEN** клиент подписан на orderbook://<figi>/20 и стакан меняется
- **THEN** сервер отправляет resources/updated для этого URI, после чего повторное чтение возвращает изменённый снэпшот

#### Scenario: Отписка
- **WHEN** клиент вызывает unsubscribe для orderbook://<figi>/20
- **THEN** сервер больше не отправляет resources/updated по этому URI

#### Scenario: Общий стрим на несколько подписчиков
- **WHEN** два клиента подписаны на стакан одного figi
- **THEN** сервер ведёт один стрим на figi и обслуживает обоих

### Requirement: Устойчивость потока
Сервер SHALL переживать разрывы стрима стакана: переподключение и возобновление подписки происходят автоматически, подписка ресурса при этом не отменяется.

#### Scenario: Разрыв соединения
- **WHEN** стрим стакана обрывается по сети
- **THEN** сервер переподключается и продолжает отправлять updates без повторной подписки клиента

## Context

Проект greenfield. Доступные строительные блоки: SDK yatis v0.2.1 (единый unary-метод request(Req) для всех сервисов T-Bank Invest API; server-side стримы order_state_stream, trades_stream, portfolio/positions и market data через start_stream с авто-реконнектом и ресабскрипцией; Api (боевой) и SandboxApi (песочница); pool соединений; rust_decimal уже в зависимостях) и официальный Rust MCP SDK rmcp (ToolRouter с макросами, resources с subscribe, нотификации, Streamable HTTP transport). Мотивация и границы scope — см. proposal.md. Все REQUIREMENTS — в дельта-спеках capabilities.

## Goals / Non-Goals

**Goals:**
- Один бинарник: MCP-сервер (Streamable HTTP) + адаптер yatis + движок стратегий + глобальный sh-хук.
- События заявок и цены приходят push-ом из стримов yatis (без polling).
- Стратегии декларативные, корректируемые на лету, автономные в обоих режимах подтверждений.
- Минимальный риск в гипер-экосистеме: tonic 0.13 (yatis) + HTTP-транспорт rmcp в одном процессе.

**Non-Goals:**
- Бид-стримы yatis (в SDK не реализованы), стримы last-price/trades как MCP-ресурсы.
- Авторизация/аутентификация HTTP-эндпоинта (локальный запуск на 127.0.0.1).
- Персистентность стратегий между перезапусками сервера (движки живут в памяти).
- Мультиаккаунтность в рамках одного процесса (аккаунт один, задаётся на старте).
- Трейлинг-семантика сверх once:false price-правил.

## Decisions

### 1. MCP SDK: rmcp
Выбран официальный rmcp: tokio-нативный (прямо ложится на стек yatis), ToolRouter + макрос #[tool], resources с subscribe/unsubscribe, нотификации через Peer, StreamableHttpServerConfig (stateful-сессии, allowed hosts). Альтернатива rust-mcp-sdk не взята: вне официальной экосистемы, API поверх axum глубже связывает с версиями hyper.

### 2. Транспорт: Streamable HTTP, stateful-сессии
Сервер — запущенный процесс, HTTP на 127.0.0.1:3001. SSE для response-стримов и нотификаций. stdio-вариант не рассматривается: требуются серверные нотификации (стакан, события стратегий) и подписки ресурсов, что в stdio-модели ограничено.

### 3. Структура модулей и направление зависимостей

    src/
    ├─ main.rs        // CLI (clap), config, запуск HTTP-сервера rmcp
    ├─ config.rs      // Config: env, token, account, confirm, hook, network
    ├─ sdk.rs         // YatisAdapter: Api | SandboxApi, пул, резолв аккаунта
    ├─ money.rs       // Quotation/MoneyValue ↔ десятичные строки
    ├─ resolve.rs     // InstrumentRef → figi/uid, кэш
    ├─ gateway/       // StreamRegistry: общие стримы (order_state per account,
    │                 //   last_price/orderbook per figi), диспетчер событий
    ├─ tools/         // тонкие адаптеры MCP-инструментов (instruments, orders,
    │                 //   portfolio, market, strategies lifecycle, get_accounts)
    ├─ engine/        // движок стратегий: конфиг, валидация, ref-маппинг,
    │                 //   правило-evaluation, tasks
    ├─ resources.rs   // resource template orderbook://{figi}/{depth}
    └─ hook.rs        // сериализованный исполнитель sh-хука

Инструменты не содержат бизнес-логики: преобразуют параметры → t_types, вызывают request(), форматируют ответ. Вся оркестрация (стратегии, подписки, хук) — вне tools.

### 4. Источник событий: общий реестр стримов
Единственная точка подписок: StreamRegistry. Поддерживает реф-каунтинг: order_state_stream — один на аккаунт, last_price и orderbook — один на (figi). Стратегии рассылают подписки через реестр; переиспользует автопереподключение yatis. События разлетаются по mpsc-каналам в задачи стратегий и задачи ресурсов.

### 5. Движок стратегии: задача на стратегию
Каждая стратегия — отдельная tokio-задача с собственным состоянием: ref→id маппинг, активные правила, статус. События из реестра приходят по каналу, правило-матчер ищет совпадение по активным правилам (порядок объявления), once-правила деактивируются, действия выполняются последовательно, результаты идут в хук и в снапшот get_strategy. Валидация конфига — отдельный модуль, общий для run_strategy и update_strategy.

### 6. Хук: глобальная сериализованная очередь
ExecutionLoop с одним потребителем: события ставятся в очередь в порядке возникновения, скрипт запускается через tokio::process::Command (stdin piped), таймаут tokio::time, kill по истечении, stderr в лог. env: YATIS_STRATEGY_ID, YATIS_EVENT_TYPE. Без --hook — очередь не подключается, события только логируются.

### 7. Деньги: единый конвертер
money.rs: единые функции Quotation ↔ rust_decimal/строки для входа и выхода; используется всеми инструментами и движком; проверяется юнит-тестами (включая отрицательные и малые величины, nano-точность).
### 8. Идемпотентность и ref-маппинг
Для place_order/replace_order сервер генерирует idempotency-ключ (uuid v4), если не передан. В стратегиях ref — единый адрес заявки/стоп-заявки внутри движка; маппинг ref → order_id/stop_order_id хранится в состоянии задачи, переживает update_strategy, умирает при get_strategy снапшоте и cancel.

### 9. Прайс-пороги и тройная проверка
price-правила матчатся по последней цене из last_price стрима. Для стабильности используются детерминированные сравнения на rust_decimal. Движок дедуплицирует повторные события (сторона: per ref и per level правило with once).

### 10. Гейтинг confirm — в слое tools
Проверка confirm выполняется в обёртке торговых инструментов на основе config.confirm_orders. Движок стратегий вызывает yatis напрямую через адаптер, минуя слой tools, поэтому гейтинг на стратегии не распространяется (зафиксировано в спецификации strategies).

### 11. Стакан как ресурс
resources.rs реализует resource template orderbook://{figi}/{depth}: read_resource отдаёт последний снэпшот из общей подписки orderbook-стрима; subscribe регистрирует сокет/Peer клиента; при каждом OrderBook из yatis шлётся resources/updated по соответствующему URI. Общая подписка на figi живёт, пока есть подписчики.

## Risks / Trade-offs

- [Версии hyper/axum: tonic 0.13 (yatis) + HTTP-транспорт rmcp в одном бинарнике] → На первом же спринте проверить cargo tree; адаптер sdk спрятан за трейтом, при конфликте — отдельный crate или временный stdio-фолбэк транспорта.
- [API rmcp для ресурсных нотификаций может отличаться от примера] → Ранний spike: заглушка сервера с orderbook-ресурсом и нотификацией до полной реализации.
- [Шторм событий частичного исполнения] → once-семантика правила + дедупликация по (ref, тип события); повторные события не матчатся.
- [Рыночное закрытие позиций в cancel_strategy скольжением] → Дефолт scope=strategy (только инструменты стратегии), scope=all требует явного выбора; результаты очистки видны в ответе и хуке.
- [Хук-скрипт встал в очередь] → Таймаут с kill; очередь ограничена; падение скрипта не влияет на движок.
- [Стрим заявок общий для всех стратегий: событие одной стратегии может читать другая] → Реестр фильтрует по account и по известным order_id стратегий (маппинг ref), чужие события игнорируются.

## Migration Plan

Greenfield: развёртывание = сборка бинарника + запуск с ключами. Откат не требуется (нет предыдущей версии). Порядок: spike по rmcp (ресурсы/нотификации) → скелет сервера → инструменты → движок → хук → интеграционные проверки на sandbox-токене.

## Open Questions

- Персистентность стратегий при перезапуске сервера (восстановление ref, позиций) — отложено, движки в памяти.
- Поддержка expire_date/глубины стакана > 50 — по запросу брокера вне скоупа.
- Кастомные нотификации событий стратегий в MCP (помимо sh-хука) — возможно позже через те же resources/updated.
